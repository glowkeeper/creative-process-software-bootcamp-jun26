# You Built More Than an Application

You practised how to:

- Break an idea into smaller steps
- Read and change code
- Investigate problems
- Test what you built
- Make and explain decisions
- Keep going when the route changed

<!--
Recognise the less visible work behind each project.

The application matters, but so do the habits and decisions that produced it.
Avoid comparing projects by feature count or visual polish.
-->

---

# Your Project Does Not Need to Be...

- Polished
- Complete
- Free from every problem
- The same as anybody else's

## Show what exists and explain it honestly.

<!--
Repeat the Week 7 reassurance before anyone presents.

Incomplete work can provide strong evidence of planning, problem-solving and
learning. This is a showcase of development, not a product competition.

# Tell the Story of Your Project

1. What did you set out to build?
2. What did you actually build?
3. Show us one part of it.
4. What decisions did you make?
5. What challenged you, and how did you respond?
6. What did you learn, or what would you do next?

<!--
These are prompts, not six equally weighted sections and not a script that must
be followed word for word.

A possible shape remains:

- about one minute for intention and current outcome
- about two minutes for the demonstration
- about one minute for decisions and challenges
- about one minute for learning and next steps

A clear three- or four-minute presentation is completely acceptable.
-->

---

# Show What Helps You Explain

You might use:

- Your application
- A deployed or local version
- Screenshots or a short recording
- Selected code
- Brief notes or a small number of slides

## Your explanation is the most important part.

<!--
Slides are optional.

Learners do not need to use every kind of evidence. They should show only what
helps the audience understand the project and its development.
-->

---

# If the Demonstration Does Not Open

Use your fallback:

1. Project running locally
2. Previous working version
3. Screenshots or a short recording
4. Selected code and an explanation

## A technical problem does not erase your work.

<!--
The preferred route is a tested deployed GitHub Pages version where available.

If it does not open, move calmly to the prepared fallback. Avoid using another
learner's presentation time for extended troubleshooting.
-->

---

# While Somebody Else Presents

Listen for:

- A decision they made
- A challenge they worked through
- Something they learned
- Something you would like to understand better

## Ask curious, supportive questions.

<!--
Set the audience expectation before the first presentation.

Questions and feedback should help the presenter say more about their thinking.
They are not a design critique or a list of features the presenter should have
built.
-->

# What Comes Next?

Choose one way to continue:

- Keep improving this project
- Build something small and different
- Revisit something you do not fully understand
- Share your work and ask for feedback
- Keep a record of what you learn

> You do not need to know everything.  
> You need a next step you can take.

<!--
This is an invitation, not a new assignment.

Encourage each learner to choose one realistic next action. Their next project
does not need to be larger or more technically ambitious; it only needs to give
them another opportunity to practise and learn.
-->

---

# Keep the Cycle Going

```text
Choose → Build → Test → Learn → Share
```

Your next project does not need to be bigger.

## It only needs to teach you something new.

<!--
Connect the close to the development practices used throughout the bootcamp.

Learner independence grows through repeated, manageable cycles rather than one
large leap.
-->
